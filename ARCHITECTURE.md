# Architecture

## Modules

- **StudyPilotCore**: Codable, Sendable value records; assignment progress/rescheduling; deterministic spaced repetition and calendar study allocation; recoverable timer state; study streaks and criterion averages; wiki-link extraction; versioned backup validation and encoding. No UI or database dependency.
- **StudyPilotData**: eleven concrete SwiftData `PersistentModel` classes; schema/container creation; subject presets; complete snapshots and ID-based restoration. SQLite persistence remains Apple's SwiftData implementation, explicitly configured without CloudKit.
- **StudyPilot**: SwiftUI features, application navigation, native search palette, backup panels, reminder service, and focus controller. UI and model mutations run on the main actor.

## Models and observation

Models are generated from `Scripts/generate-models.py`, which produces both public value records and the SwiftData implementations. Complex checklist and tag arrays are JSON-encoded in Data properties; all other values are native scalar attributes. UUIDs are unique identifiers. Cross-record references use UUIDs rather than relationships, keeping the export schema explicit and restorable.

The host's standalone Command Line Tools SDK contains SwiftData but not the `SwiftDataMacros` compiler plug-in. Explicit conformances implement the same storage protocol using `BackingData`, `Schema.PropertyMetadata`, `getValue`, `setValue`, and `ObservationRegistrar`. They are real persistent models, not mock objects. Do not switch to Apple's `Query` macro without moving back to models generated by `@Model`: Query relies on additional macro-emitted runtime metadata. The small `LiveQuery` wrapper instead fetches through `ModelContext`, observes committed saves, and exposes observable arrays to SwiftUI. This path was exercised in the running app after an initial Query metadata failure was found.

Each feature loads its model arrays, and the wrapper refreshes after committed changes. Filters are in memory, appropriate for a personal workspace. The backup limit is a validation ceiling, not a promise of smooth UI performance with 100,000 records. Large-scale use would require paged queries and indexed searches.

To regenerate models or update source references in the Xcode project:

```sh
python3 Scripts/generate-models.py
python3 Scripts/generate-xcode.py
```

Before changing a shipped schema, add a versioned migration plan and test it against copies of prior databases. This is the initial schema, with no previous production version to migrate.

## Save boundaries

Editing sheets use value drafts. Save applies a record and commits the context; cancellation keeps the original unchanged. Note edits are observed and explicitly saved after a 400 ms debounce, with another save on leaving the editor. SwiftData autosave remains enabled as an additional safeguard. Save errors appear to the user rather than disappearing silently. Review ratings commit the card update and history record together; failure rolls the context back.

Deletion controls for persisted assignments, notes, events, cards, decks, and assessment results require explicit confirmation. Deck deletion includes its cards and reviews. Subject, notebook, and project editing is supported without destructive deletion controls. Unsaved subtask changes can be cancelled with the assignment sheet.

## Revision schedule

All calculations accept an explicit clock and calendar:

| Rating | Next interval | Ease change |
| --- | --- | --- |
| Again | 10 minutes; reset repetitions | −0.20, floor 1.30 |
| Hard | max(1, round(previous days × 1.2)) | −0.15, floor 1.30 |
| Good | 1 day, then 3 days, then round(previous days × ease) | unchanged |
| Easy | 4 days initially; then max(4, round(previous days × ease × 1.3)) | +0.15, ceiling 3.00 |

Day intervals use calendar arithmetic to preserve local time across daylight-saving changes. Intervals are bounded at 36,500 days. Again increases lapses and resets repetitions. Hard/Good/Easy count as successful recall for the displayed accuracy. Empty history displays no accuracy estimate.

## Timer reliability

`FocusState` stores a stable session UUID, start time, duration, remaining seconds at an anchor date, and optional running anchor. Pausing converts elapsed wall time into remaining seconds; resuming sets a new anchor. The one-second publisher only redraws and reconciles state; it is not the time source. UserDefaults preserves the state across termination. A completed session is saved with its stable ID before the active state is cleared. Retrying after a crash cannot insert the same session twice. If saving fails, automatic retries pause and the active state is retained for an explicit retry.

## Backup safety

`BackupCodec` validates all records, relationships, IDs, numeric ranges, text limits, schedules, and supported versions. Restoration checks everything before mutation, temporarily disables autosave, updates matching IDs, inserts new IDs, removes absent IDs, and saves once. Failure rolls back pending changes. The UI creates a complete pre-restore snapshot first; if this backup cannot be written, restoration never begins. JSON writes use atomic replacement.

The application does not upload the workspace database or use an analytics SDK. Local notifications use UserNotifications. The optional calendar workflow writes reviewed changes to the selected EventKit calendar; macOS syncs these to that calendar's provider. Local AI receives the task context or selected source excerpts described by each feature. Chat context settings control access to workspace/calendar context; notebook questions use only checked source excerpts.

## Google Calendar and study planning

`CalendarPlanningService` owns one EventKit store. The user connects Google through macOS Calendar and grants calendar access through the native permission prompt. The service reads selected deadline/busy calendars and the selected writable destination over a bounded time window. Calendar events are snapshots, not SwiftData imports. Declined/cancelled events are excluded, free events do not block time, selected assignment events become deadline constraints, and all-day deadline events use the last minute before their exclusive end date. Recurring occurrences receive distinct identities.

`StudyPlanner` allocates work by deadline, then priority, within user-selected weekdays/hours, a daily cap, session lengths, and breaks. Work rounds up to five minutes. Intervals use absolute dates and injected Calendar arithmetic across daylight-saving changes. Existing future StudyPilot blocks count toward a task's remaining work and daily budget. Past sessions do not imply task completion. Work that cannot fit produces an explicit unscheduled item. Allocation is deterministic for the same inputs; new block UUIDs are storage identifiers.

Optional local AI produces reviewed remaining-time ranges through `TimeEstimateGeneration`. It uses the selected Apple or Qwen model; invalid responses leave existing fields untouched. Suggested assignment steps were removed in 1.9.1. AI does not choose event times or perform writes. Unsupported/unavailable models retain automatic scheduling with manually entered estimates.

The preview is invalidated by input changes. Before saving, the app checks the current local database and refetches calendar events. Calendar changes require a new preview. Calendar writes are staged with `commit: false` and committed together; an error resets the store and requires refresh. New events have a StudyPilot URL and encoded source-task identity in their notes so subsequent plans recognize already allocated work. Existing events, teacher deadlines, and recurring series are never changed by this workflow. Local saves use existing PlannerEvent records, so the database schema remains unchanged.

Planning preferences and reviewed task inputs are stored in an atomic sidecar JSON file beside the store, with calendar descriptions omitted. They are not portable workspace backup data. Google authentication and synchronization remain managed by macOS. A live account is required to verify provider sync and real write permissions.

## Notebook research

`NotebooksView` presents the existing Notebook records as a library and source workspace. Imported extracted text is stored in independent Note records marked `studypilot:source`; saved AI answers use `studypilot:answer`. This keeps portable backup compatibility without altering SwiftData schema. Hidden internal tags are preserved when users edit ordinary note tags. File imports extract PDF text with page markers or read UTF-8 Markdown/plain text in a detached task. Transaction contexts disable autosave and commit each copy once, validating source size, per-notebook capacity, and exact duplicates before insertion.

`NotebookResearch` splits material into stable non-overlapping excerpts, matches query terms (including CJK bigrams), and bounds model context to eight excerpts. When nothing matches it samples across sources. `NotebookResearchController` owns cancellable request identity, selected-model dispatch, and validated response decoding. Source/question/model changes invalidate results. IDs must refer to supplied excerpts; citations display the original stored excerpt text. Identity validation does not prove a synthesized explanation is entailed by a source. Saving an answer explicitly stores its question, model label, and quoted passage snapshots in a normal notebook note.
